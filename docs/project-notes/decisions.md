# 기술 선택 기록

## 2026-09-22 · Vue 패키지는 hanui 모노레포에 유지

**상태: 확정 (재검토 조건 명시)**

### 결정

`packages/vue`를 별도 저장소로 분리하지 않고 `repos/hanui` 모노레포에 둔다.

### 이유

- 문서 사이트(`apps/docs`, hanui.io)·`packages/registry`·`packages/cli`가 같은 저장소에 있다. 분리하면 셋 다 크로스 리포 의존이 되어 문서 한 건 수정에도 두 저장소를 오가야 한다.
- "Vue 집중 범위·React 유지 범위"가 미확정이다. 지금 분리하면 그 결정을 구조로 먼저 고정하게 된다.
- 분리로 얻는 이점(독립 도구 설정, 독립 버전)은 모노레포 안에서도 가능하다. 패키지 자체 eslint/vitest/vite/storybook 설정, prettier 훅에서 vendor 제외, changeset 패키지 단위 버전으로 이미 격리했다.

### 유지 조건

- `packages/vue`는 루트 Tailwind/PostCSS·React 패키지에 의존하지 않는 독립 실행 상태를 유지한다. 필요 시 `git subtree split`으로 이력 포함 분리가 가능해야 한다.
- 루트 Prettier/lint 훅은 `packages/vue/vendor/`를 건드리지 않는다.

### 재검토 조건

다음 중 하나가 발생하면 분리를 다시 판단한다.

1. React 패키지 공식 종료와 문서 사이트의 Vue 전용 재편 결정
2. Vue 패키지에 별도 릴리스 주기 또는 별도 담당자가 생김
3. 외부 협업자에게 Vue 패키지만 공개·권한 부여해야 함

## 2026-09-22 · Vue 패키지 재구축 방식

**상태: 확정**

기존 Tailwind/cva 기반 Vue 컴포넌트를 폐기하고 KRDS HTML ComponentKit 리소스를 그대로 사용하는 얇은 래퍼로 새로 만든다.

- KRDS 원본(`resources/`, `tokens/`)은 `packages/vue/vendor/krds-uiux/`에 통째로 두고 수정하지 않는다. 업데이트는 폴더 교체와 `VERSION.md` 갱신이다.
- 스타일은 KRDS SCSS를 그대로 컴파일한다. **hanui 확장 스타일은 추가하지 않는다** (2026-09-22 확정. 처음 넣었던 Button loading 스피너도 제거). KRDS에 없는 상태가 필요하면 컴포넌트 추가 전에 별도 결정한다.
- 범위는 최소 기능 CMS(공지 작성→미리보기→게시→공개 목록·상세, 로그인, 관리자 레이아웃)에 필요한 컴포넌트만 만든다. KRDS 39개 전체 구현은 목표가 아니다.
- Vue 컴포넌트는 KRDS 클래스 조립·동작·접근성만 담당한다. `ui-script.js`의 전역 초기화 방식은 Vue 동적 렌더와 맞지 않으므로 동작은 Vue로 재구현하고 원본은 참조 기준으로만 쓴다.
- 컴포넌트마다 테스트·Storybook 스토리·브라우저 확인을 함께 만든다. Button으로 이 패턴을 먼저 확정했다.

## 2026-09-21 · Vue 중심 개발 방향

**상태: 선호 방향 기록 / 전환 범위와 실행 계획은 미확정**

### 사용자가 설명한 배경

- 정부·공공기관 웹 구축 입찰과 납품이 목적이다.
- 프로젝트마다 참여하는 개발자가 달라지고, 바쁜 일정 때문에 새 기술을 충분히 공부할 시간이 부족하다.
- 사용자의 실무 경험상 Vue를 사용하는 경우가 많고, React의 설정과 학습이 참여자에게 부담이 될 수 있다.
- 전자정부프레임워크의 React 예제 제공과 실제 납품 현장의 기술 선택은 구분해서 본다.
- React와 Vue를 동시에 유지하다가 둘 다 완성도가 부족해질 것을 우려한다.

공공·금융 전체에서 Vue 사용률이 더 높다는 통계가 확인된 것은 아니다. 위 내용은 사용자가 관찰한 실무 환경과 선택 이유로 기록한다.

### 현재 논의 방향

Vue에 집중하는 방안을 우선 검토한다. 기존 React 코드의 양뿐 아니라 실제 협업할 사람들이 빠르게 이해하고 유지보수할 수 있는지를 중요한 기준으로 삼는다.

HANUI의 목표는 컴포넌트 제공에 더해, 참여자가 일관된 패턴으로 화면을 만들 수 있는 기반을 제공하는 것이다. 폼 검증, API 연결, 로딩·오류 처리, 접근성 사용 예제를 함께 정리하는 방향을 제안했다.

### 제안된 진행 방법 — 아직 실행하지 않음

1. 기존 React 코드는 보존하고 양쪽 기능을 동시에 확장하는 작업은 보류한다.
2. 기존 Vue 컴포넌트의 실제 구현과 검증 상태를 점검한다.
3. Vue로 게시판 목록 → 상세 → 등록·수정 흐름을 구현해 적용성을 확인한다.
4. 결과를 바탕으로 CMS 전환 범위와 공통 개발 규칙을 확정한다.

### 남은 판단

- 컴포넌트만 Vue에 집중할지, CMS 공개·관리자 화면도 전환할지
- Vue 앱 구성 방식과 배포 환경
- React 패키지 및 기존 문서 사이트의 유지 범위
- 협업 대상 개발자의 기술 경험과 실제 대상 사업의 요구사항

Vue 코드와 CLI는 이미 존재하지만 정상 동작과 배포 준비 상태는 미확인이다. 현재 CMS는 Next.js·React 기반이며 이 기록은 이식 완료나 즉시 재작성 지시를 의미하지 않는다.

## 2026-09-21 · 백엔드 전자정부 표준프레임워크 v5 채택

**상태: 사용자 지정으로 확정 / 적용·실행 검증 전**

HANUI CMS 백엔드는 **전자정부 표준프레임워크(eGovFrame) v5**를 사용한다. 프론트엔드 선택과 별개로 유지하는 기술 요구사항이다.

- 공식 출처: [eGovFramework 저장소 목록](https://github.com/orgs/eGovFramework/repositories)
- 적용 후보 확인: [백엔드 템플릿](https://github.com/eGovFramework/egovframe-template-simple-backend), [실행환경](https://github.com/eGovFramework/egovframe-runtime), [공통컴포넌트](https://github.com/eGovFramework/egovframe-common-components)
- 위 저장소들은 공식 목록에서 존재를 확인했다. 사용할 v5 태그·릴리스, JDK·Spring Boot 호환 버전과 도입할 공통 기능은 별도로 확인한다.
- 기존 `hanui-cms/apps/backend` 소스를 먼저 점검하고, 재사용 가능한 코드와 v5 적용에 필요한 변경을 구분한다.
- Vue 화면과 백엔드는 API로 연결하는 구성을 지향한다. 인증·권한·파일 업로드·게시판의 계약과 오류 응답을 먼저 정리한다.

프레임워크 선택은 확정했지만 저장소 전체 복제, 의존성 변경, 백엔드 재작성은 아직 수행하지 않았다.

## 2026-09-21 · 작업 모델과 검증 원칙

**상태: 작업 운영 원칙으로 확정**

작업 속도를 위해 Luna Light를 기본 모델로 사용한다. 각 단계에서 타입 검사·테스트·빌드·필요한 브라우저 및 접근성 검증을 실행하고, 검증 결과가 통과하지 않으면 완료 또는 OK로 표시하지 않는다.

다음 경우에는 더 강한 모델의 독립 검토가 필요하다고 알린다.

- 설계·기술 선택 또는 기존 구조의 큰 변경
- 접근성·보안·권한·게시 상태처럼 실수 비용이 큰 영역
- 여러 파일에 걸친 테스트 실패 원인 추적
- 최종 품질 검토와 출고 판정

모델 변경 자체를 품질 보증으로 간주하지 않는다. 최종 OK는 실행 가능한 검증 결과와 코드 검토 근거를 함께 확인한 뒤 기록한다.

## 2026-09-21 · v0 CMS와 KRDS 적용 전략

**상태: v0 범위와 구현 순서 확정**

첫 목표는 공공기관 대표 홈페이지 CMS v0이다. 전체 CMS나 125개 Vue 컴포넌트를 먼저 완성하지 않고, 로그인·관리자 레이아웃·공지 작성/수정·미리보기·게시·공개 목록/상세의 작은 세로 흐름을 먼저 완성한다.

이 흐름에 필요한 Button, Input, Textarea, Select, FormField, Table, Pagination, Modal, Alert/Toast, Card, Header, SideNavigation, Breadcrumb부터 검증·전환한다. 실제 사용 결과를 바탕으로 토큰과 컴포넌트 API를 보정한 뒤 나머지 컴포넌트를 확장한다.

**상태: 스타일 구조 확정 방향**

- KRDS 토큰을 CSS 변수의 기준으로 둔다.
- primitive token, semantic token, component token, typography/spacing/motion을 중앙에서 관리한다.
- 컴포넌트 스타일은 중앙 CSS에서 관리한다. 컴포넌트별 `<style scoped>`와 Tailwind 클래스에 스타일을 분산하지 않는다.
- Vue 컴포넌트는 `variant`, `size`, 상태 클래스와 Vue 동작만 제공한다.
- Tailwind는 v0 컴포넌트 스타일의 기준으로 사용하지 않는다. CLI 소비자 프로젝트용 preset/theme는 별도로 유지할 수 있다.

**상태: KRDS 원본 적용 원칙 확정**

공식 [KRDS-uiux 저장소](https://github.com/KRDS-uiux/krds-uiux)를 `reference/krds-uiux`에 클론해 기준 소스로 사용한다. KRDS HTML·CSS·JS·토큰을 그대로 복사해 Vue로 포팅하지 않는다. 원본은 DOM 구조·상태·토큰·접근성 관계를 대조하는 기준으로 사용하고, Vue의 `v-model`, 슬롯, 이벤트, FormField 컨텍스트와 CMS 상태를 결합한 중앙 CSS와 동작으로 재작성한다.

현재 모델로 구현한 뒤 타입 검사·테스트·빌드·브라우저 검증을 실행한다. 이후 더 강한 모델이 KRDS 대조, 접근성, 권한·게시 상태, API와 토큰 구조를 독립 검토한다. 지적 사항을 수정하고 검증을 다시 실행하기 전에는 OK로 기록하지 않는다.

## 2026-09-30 · KRDS 원본 CSS 결함 보완 방식

**상태: 사용자 확정**

2026-09-22부터 Vue 패키지는 KRDS 리소스(CSS·토큰·아이콘)를 vendor로 그대로 쓰고 vendor는 수정하지 않는다(→ tasks.md "Vue 패키지 재구축"). 이 원칙은 유지하되, KRDS 원본 CSS 결함 중 **공공기관 검수에 걸리는 것**은 hanui 보완 CSS 한 파일로 덮어쓴다.

- 위치: `packages/vue/src/styles/_hanui-fixes.scss`, `index.scss`에서 KRDS 다음에 불러온다.
- 규칙마다 KRDS 버전과 근거를 주석으로 남기고, KRDS 업데이트로 원본이 고쳐지면 해당 규칙을 지운다.
- 새 디자인을 추가하지 않고 KRDS 토큰 값만 쓴다.
- 보완 대상 목록은 `krds-source-audit.md`의 원본 결함 기록과 대조한다.

첫 적용(KRDS v1.1.0): ① Footer 개인정보처리방침 `.point` 강조(원본 CSS 정의 없음) ② Breadcrumb 모바일 숨김 항목에 초점이 들어오면 표시(WCAG 2.4.7).

아직 보완하지 않은 CSS 결함: Badge outline 테두리 변수 오류(화면 차이 작음), Spinner `prefers-reduced-motion` 미대응(AAA). 검수 영향이 확인되면 같은 방식으로 추가한다.

## 2026-09-30 · Vue CMS 구성·배포 방식

**상태: 사용자 확정**

- 위치: `repos/hanui-vue-cms` 저장소, pnpm 모노레포. 컴포넌트 라이브러리(`repos/hanui/packages/vue`)와 저장소를 분리한다.
- 공개 사이트(`apps/public`): **Nuxt(SSR)**. 검색엔진(특히 네이버·다음) 수집과 카카오톡 등 링크 미리보기(OG 태그)는 JS를 실행하지 않거나 불안정하므로 서버에서 완성된 HTML을 보낸다. 운영은 Docker 온프레미스 안에 Node 컨테이너를 둔다.
- 관리자(`apps/admin`): **Vite SPA**. 로그인 뒤 화면이라 검색 노출이 필요 없고, 내부망·IP 제한으로 분리 배포할 수 있게 공개 사이트와 앱을 나눈다.
- 공개 화면 본문은 `packages/views`에 두어 공개 앱과 관리자 미리보기(M06)가 같은 컴포넌트로 렌더한다.
- API 계약 타입·클라이언트는 `packages/api`, 기관 정보·메뉴 구조는 `packages/site-config`.
- 백엔드(전자정부 v5)가 붙기 전까지 데이터는 API 계약 형태의 임시 mock으로 채운다. **mock 상태의 화면 조립은 납품 완료나 A01~A02 통과로 기록하지 않는다.**
- 개발 중 `@hanui/vue`는 `link:`로 연결한다. 배포는 공개 npm(아래 2026-10-01 결정).

## 2026-10-01 · Vue 컴포넌트 패키지 공개 npm 배포

## 2026-10-02 · API 계약(OpenAPI)과 백엔드 보안 기본값

**상태: 제안 — 백엔드 착수 때 확정** (계약 문서: `repos/hanui-vue-cms/packages/api/openapi.yaml`)

- 화면이 쓰는 공개·관리자 API 전부를 OpenAPI 3.1로 고정했다. TypeScript 타입(`packages/api/src/*types.ts`)과 같은 내용이며, 계약 테스트(`contract.test.ts`)가 mock 서버의 실제 요청·응답을 이 문서로 검사한다. 계약을 바꾸면 문서·타입·mock·테스트를 함께 바꾼다.
- 인증: **HttpOnly·Secure·SameSite=Lax 세션 쿠키** + **CSRF 토큰**(Spring Security 쿠키 방식 `XSRF-TOKEN` → `X-XSRF-TOKEN`). mock의 Bearer 토큰·로그인 응답 `token`은 개발용이다. 백엔드가 붙을 때 관리자 API 클라이언트(`admin-client.ts`)를 쿠키·CSRF 방식으로 바꾼다(sessionStorage 토큰 제거).
- 배치: 공개·관리자 화면과 API를 같은 사이트(리버스 프록시 아래 같은 도메인)에 둔다 — 쿠키·CSRF 처리를 단순하게 하고 CORS를 열지 않는다.
- 본문: `bodyJson`(Tiptap 문서)이 원본. 서버는 허용 노드·마크만으로 `bodyHtml`을 다시 만들고 브라우저가 보낸 HTML은 믿지 않는다. 파일은 확장자와 내용(시그니처)을 모두 확인한다.
- 비밀번호는 적응형 해시(bcrypt·scrypt·Argon2). 초기화·변경·사용 중지 때 그 계정의 세션을 무효화한다. 로그인 잠금은 계정 단위 + IP 기준 제한을 함께 검토한다.
- 오류 응답 모양(`message`·`fieldErrors`·`issues`·`code`)과 상태 코드 의미(400·401·403·404·405·409·429)를 계약에 적었다. 관리자 API는 모두 401·403을 돌려줄 수 있다.

## 2026-10-06 · 구축·운영 두 가지 작업 방식

**상태: 사용자 확정** — 계기: 실제 작업은 "개발자가 HTML·CSS·이미지로 만들고 담당자 컨펌 → 본문만 붙여 넣기"이고, 납품 후에는 직원이 CMS로만 고친다. 이미지를 한 장씩 올리면 작업이 너무 많다.

| | ① 구축 (개발자) | ② 운영 (납품 후 직원) |
| --- | --- | --- |
| 본문 | HTML 소스에 붙여 넣기 | 텍스트 수정(구조 잠금) |
| 이미지 | 여러 장·폴더째 올리기 → 파일 이름(+폴더 이름)으로 짝 맞춤, 올리기 전 확인 | 본문 이미지 목록에서 [교체]·대체텍스트 |
| CSS | 사이트 전용 CSS(`packages/site-config/src/site.css`, 코드로 관리·배포) | 손대지 않음 |
| 오류 | 자동 고치기 + 직접 수정 | 게시 전 검사 안내대로 |

- 이미지 경로 형태는 표준이 없다(상대·루트 기준·전체 주소). 어느 형태든 파일 이름으로 짝을 맞추고, 같은 이름이 여러 폴더에 있으면 폴더 이름까지 비교, 그래도 겹치면 모호하다고 알린다.
- 교체: 같은 주소는 모두 바뀐다. 예전 파일은 지우지 않는다(안 쓰이면 방문자에게 열리지 않음, 정리는 추후).
- 자동 고치기: 규칙만으로 되는 것만(h1→h2, 빈 제목 삭제, 예약·형식 위반 id 이름 바꾸기와 참조 갱신, 중복 id 번호, 새 창 링크 안내, 표 th scope). 바꿀 목록을 보여 주고 적용해야 바꾼다. 대체텍스트 내용·링크 문구·글자색·제목 단계 건너뜀은 고치지 않는다(다음 차수 AI 도우미에서 제안).
- HTML 소스 편집은 기존 결정대로 관리자·담당자 모두 가능(추천대로 유지).
- 구현: hanui-vue-cms `3efcd0e`(이미지 목록·폴더 올리기), `04ac9f0`(site.css), `59724fc`(자동 고치기).

## 2026-10-06 · 외부 이미지는 막고, 한 번에 가져오기 제공

**상태: 사용자 확정** — 계기: 서울시 HTML을 넣으니 외부 이미지 29개가 "업로드하지 않은 이미지" 오류로 29줄 나왔다.

- 외부 이미지 직접 표시는 계속 막는다(원본 변경·삭제로 화면 깨짐, 방문자 IP가 외부로 전달, CSP `img-src` 개방 필요).
- 대신 **"외부 이미지 가져오기"**: 서버가 사이트 설정 `imageImportDomains`(하위 도메인 포함)의 https 이미지만 내려받아 업로드 파일로 저장하고 본문 src를 바꾼다. 대체텍스트는 그대로.
- SSRF 방어: 허용 도메인 + DNS 확인 주소가 내부망이면 거부 + 리다이렉트마다 재검사(3번까지) + 10초·20MB 제한 + 파일 내용(시그니처) 확인. 실제 백엔드는 확인한 주소로 직접 연결(DNS rebinding 방지).
- 같은 종류 검사 결과는 3개 이상이면 한 줄로 묶는다(오류 요약·게시 전 검사, 펼치면 항목별 이동).
- 구현: hanui-vue-cms `eee11ab`.
- 한계: mock의 내부망 차단은 계약 테스트에서 직접 확인하지 못했다(시험 서버가 로컬이라 시험 전용 허용 설정을 씀). 실제 백엔드 구현 때 단위 테스트 필요.

## 2026-10-06 · 본문 인라인 style 일부 허용 (기관 설정)

**상태: 사용자 확정** — 계기: 서울시 누리집 HTML을 붙여 넣으니 `style` 31개(표 `col` 너비 등)가 지워졌다. 판매하는 CMS라 기존 관공서 HTML 이전이 어려우면 단점이 된다.

- `on*` 이벤트 속성은 지금처럼 **항상 지운다**(스크립트 실행 → 계정 탈취). `style`은 스크립트를 실행하지 못하고 위험은 화면 덮기(가짜 로그인 창)·외부 주소 호출 정도라 범위를 정해 허용한다.
- 기관 설정 `contentStyle`(사이트 설정 화면):
  - **limited(기본, 일부 허용)**: 너비·높이·정렬·여백·테두리·글자색·배경색·굵기·글자 크기 등 허용 목록만 남긴다. `position`·`z-index`·`top` 등(화면 덮기), `background`·`url()`(외부 주소), `display:none`·`opacity`·`visibility`(숨기기), 음수 여백, 따옴표·역슬래시·주석이 든 값은 지운다.
  - **strict(모두 지움)**: 이전 규칙. 보안 요구가 높은 기관용.
- CSP: limited면 `style-src-attr 'unsafe-inline'`만 풀고 스크립트 규칙은 그대로. strict면 풀지 않는다. 대상 브라우저의 `style-src-attr` 지원은 납품 전 확인(미확인).
- 인라인으로 색을 바꾼 글자는 게시 전 검사에서 대비를 계산한다(3:1 미만 게시 차단, 3~4.5:1 권고 — 큰 글자 여부는 판단하지 않음).
- 설정을 바꿔도 이미 저장된 본문은 다음 저장 때 새 규칙으로 정리된다(일괄 재정리는 하지 않음).
- 구현: hanui-vue-cms `34b118f` (`html-policy.ts` cleanStyle, `GET /api/admin/content-policy`, 사이트 설정 선택, `content-check.ts` color-contrast).

## 2026-10-02 · 본문은 HTML이 원본 (SI 퍼블리싱 소스 투입 + 운영자 텍스트 수정)

**상태: 사용자 확정** — 이유: 정부 홈페이지 SI가 사용하는 CMS다. 퍼블리셔가 HTML로 제작한 소스를 넣고, 운영자는 텍스트 정도를 고친다. 따라서 HTML 작성이 가장 기본이어야 한다.

- 고정 페이지·게시글 모두 **`bodyHtml`이 원본**이다. 편집기 문서(JSON) 원본 방식(2026-10-02 API 계약 결정의 해당 항목)은 폐기한다.
- 편집 방식 세 가지: **HTML 소스**(좌우 분할 실시간 미리보기) / **텍스트 수정**(미리보기에서 글자·대체텍스트만 고치고 태그·구조는 잠금) / **간편 편집**(제한 편집기, 단순한 글. 결과는 HTML이며, 구조가 복잡한 HTML에서는 구조 손실을 막기 위해 쓸 수 없다).
- HTML 소스 편집은 **기관 관리자·콘텐츠 담당자 모두** 가능(사용자 선택).
- 서버가 남기는 HTML: **KRDS 클래스 기반, 인라인 style 금지**(사용자 선택). → **2026-10-06 변경: 인라인 style 일부 허용(기관 설정)** — 아래 항목 참고. `class`·`id`·`aria-*`·`role`·`data-*` 등 허용, `script`·`style`·`iframe`·`form`류·`on*` 이벤트 속성·`javascript:` 링크는 제거. 허용 목록은 화면과 서버가 같은 정의를 쓰고, 실제 백엔드는 Java 정리기(jsoup Safelist 등)로 같은 목록을 구현한다.
- F08 "임의 HTML 삽입 제외"는 "허용 목록 밖 HTML은 서버가 제거"로 해석한다. 게시 전 접근성 검사는 HTML을 직접 검사한다(대체텍스트·표 제목 셀·제목 순서·링크 문구·중복 id 등).
